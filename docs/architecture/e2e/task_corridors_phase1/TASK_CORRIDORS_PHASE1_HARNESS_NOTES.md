## Fire convention

For each case the agent will:

1. Generate the envelope with deterministic IDs:
   - `tenant_id` from the case's `tenant` lane.
   - `message_id = detUuid("tcp1-2026-04-25|<case_id>|msg")`.
   - `thread_id  = detUuid("tcp1-2026-04-25|<case_id>|thread")`.
   - `idempotency_key = "tmr:tcp1-2026-04-25:<case_id>"` (TR-level; downstream tasks use the metadata-based marker generated by ME_Task_Create_Prep).
2. Stamp `fire_iso = now()` immediately before calling execute_workflow.
3. Call `execute_workflow` with `executionMode='production'` and the
   chatInput JSON-stringified TR envelope.
4. Record the returned `executionId` and `status` in
   `artifacts/runs/<run_tag>/<case_id>.json`.
5. On replay cases (TC-C11-*), the agent re-fires the SAME envelope a
   second time and records the second executionId.

## SQL invariant convention

After all cases fire, the agent runs a single batch of SELECT-only probes
that:

- Group `tasks` by `tenant_id + thread_id`, asserting per-case row deltas.
- Cross-check `tenant_a_in_default = 0` and `default_in_tenant_a = 0`
  patterns for tenant isolation.
- Verify `count(public.reminders) = 1` and `max(updated_at) = '2026-04-13T20:17:13Z'` (pre-mission row, untouched).
- Verify replay cases produced exactly 1 row each (idempotency).
- Verify `metadata->>'idempotency_key'` is populated for every chain-created row.

## Oracle treatment of `MISSING_DELIVERY_TARGET`

Per pack §rule 5: when MO returns `MISSING_DELIVERY_TARGET` (no Telegram
chat configured for the e2e tenants), the case is **not** marked failed.
The oracle asserts task module success at the SU/RA boundary
(`module_results[*].status='success'` for the create_task step) and at
the `tasks` table side-effect, not at the MO send.

## What this harness deliberately does NOT do

- It does **not** call `mcp__n8n__patch_workflow_nodes` — read/verify only.
- It does **not** propagate the TR envelope's `idempotency_key` to the
  task row's metadata marker. The downstream marker is generated in
  `ME_Task_Create_Prep` from `${env.execution_context_id}:${step.step_id}`,
  which is what makes replay invariants work without depending on
  upstream.
- It does **not** mutate any workflow unless a real task-path regression
  is observed during the run. If a regression is observed, the patch
  goes through the V2-028 canonical local CLI channel and is documented
  here.
