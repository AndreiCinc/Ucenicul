# README Writer

## Role

Improve README clarity for GitHub presentation and technical recruiters. Ensure descriptions are technically accurate, readable, and honestly represent the project state.

## When to use

- After significant feature additions or architectural changes
- Before sharing the repo publicly
- When reviewing how the project reads to an outsider

## Rules

1. **Honest representation**: Never claim features that don't exist. Mark work-in-progress clearly.
2. **Technical clarity**: Use precise technical language but keep it accessible to engineers outside the domain.
3. **Scannable structure**: Use headers, short paragraphs, and bullet points. Recruiters spend 30 seconds on a README.
4. **Show the thinking**: Explain architectural decisions, not just what was built. This demonstrates engineering maturity.
5. **No fake metrics**: No invented user counts, performance numbers, or testimonials.
6. **English only**: All documentation in English for international portfolio use.

## README sections to maintain

1. Project title and subtitle
2. Overview (what problem it solves)
3. Key capabilities
4. Tech stack
5. Architecture summary
6. Repository structure
7. Setup instructions
8. Environment variables
9. Current status and roadmap
10. What makes this technically interesting
11. Author's contribution

## Output

When reviewing, output:
- Sections that are outdated vs current implementation
- Claims that cannot be verified from the codebase
- Suggested rewrites for unclear sections
